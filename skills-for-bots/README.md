# 团队技能包

七个角色各一份，写进对应 Bot 的 `instructions`。每个包都在 700–850 字之间——足够具体到能执行，又不至于把上下文撑满。

## 为什么是这些内容

这些不是从别处抄来的 prompt 模板，是从实际踩过的坑里提炼的规则。

比如小研那份里的「工具行为的自证」：DOI 解析返回 `responseCode=2` 是连接失败，`100` 才是 handle 不存在。不区分这两者，会把服务故障误报成假文献——这个坑真踩过。

再比如审稿那份要求「每条问题给位置 + 问题 + 为什么是问题 + 最小修改」，是因为只说「这段写得不好」等于没说。

## 分配

| Bot | 技能包 | 核心内容 |
|---|---|---|
| Chief | `chief.md` | 接单三步、验收四问、退回标准、汇报口径 |
| 小研 | `xiaoyan.md` | 检索式要留痕、核验四种结论、判定优先级、工具自证 |
| 选题 | `xuanti.md` | 兴趣变问题四关、五维体检、新颖性判定、致命缺陷审计 |
| 实验 | `shiyan.md` | 五要素、可复现四件套、四类陷阱、负结果处理 |
| 写作 | `xiexie.md` | 每句有归属、段落骨架、避免的写法、待补证据清单 |
| 图表 | `tubiao.md` | 图型选择表、四个必查错误、配色、三条交付件 |
| 审稿 | `shengao.md` | 独立性、五道检查、CRITICAL/MAJOR/MINOR 分级 |

## 共同的骨架

七个包结构一致，都是四段：

1. **做法**——具体到可以照做，不是原则口号
2. **判据**——什么算完成，什么算不合格
3. **禁止**——明确列出不许做的事
4. **口径**——数字、状态、结论怎么说才不失真

最后一段最重要。科研协作里最贵的错误不是算错，是把「不确定」说成「确定」。

## 怎么应用

```bash
node apply-skills.mjs
```

脚本会读 `%APPDATA%\dsh-desktop\harness\bot\state.json`，把每个包追加到对应 Bot 的 `instructions` 末尾，并加 `<!-- skill-pack -->` 标记。

幂等：再次运行会替换标记之后的整段，不会重复堆叠。改完技能包重跑一次即可。

改之前先备份 `state.json`。

## 迭代

技能包应该跟着实际事故长。每遇到一次「Bot 又犯了某个错」，就在对应包里加一条规则，并写清这次是什么场景。

规则不是越多越好。超过一千字就该合并同类项——Bot 读不完的规则等于没有规则。
