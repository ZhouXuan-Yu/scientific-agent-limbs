## 一、实际发生了什么

建单 → dispatch 下发 → DSH 执行 → turn/end 回传 → 人工核对 → sync 归档 → done。

DSH 拿到任务单后做的工作比预期多：自己写了 `fetch_zotero.py` 分页拉数据、把 40 个原始响应落盘到 `raw/`、用 `build_report.py` 从结构化数据生成报告（不是手抄数字）、再写 `verify.py` 重新调一遍 API 逐项比对 143 项。最后回复里还主动报告了四个额外发现。

这是任务单写得够清楚的结果。`goal` 里给了三个具体接口和判定边界，它就不需要猜。

## 二、暴露的问题

### 问题 1：产物落到了错误的位置（严重）

DSH 把整个 `tasks/T20261019-03-85cc/` 建在了 `%APPDATA%\dsh-desktop\launch-root\` 下，而不是工作区。

根因：任务单渲染出的产物目录是相对路径 `tasks/<id>/`，DSH 的工作目录是它的 launch-root，相对路径就按那个解析了。

**已修**：
- `tasks.mjs` 的 `render()` 改成输出绝对路径
- `dispatch.mjs` 创建会话时传 `cwd: config().workspace`

两处都改是双保险。绝对路径保证即使 cwd 没生效也不会落错。

产物已手工迁回工作区，46 个文件 250KB。

### 问题 2：dispatch 不验证产物存在

它只等 turn/end，拿到回复就算成功。回复里说「产出 inventory.md」，实际那个文件在别的目录，dispatch 不知道。

**已修**：dispatch 完成后检查产物目录，缺失或顶层无文件时在输出里带 `artifactWarning`，并记一条 `artifact-missing` 审计。不判失败（有的任务本来就不产出文件），但必须报出来。

### 问题 3：Zotero 全文索引只到前 100 页

`IJWR4SZA`（100/143 页）、`JDS3VDSC`（100/131 页）的 fulltext 只索引了前 100 页。这是 Zotero 的限制，不是我们这边的问题，但影响很大：**如果精读卡只依赖 fulltext API，这两篇会缺后 43 页和后 31 页的内容**。

**记录，未修**。后续写精读卡时必须直读 PDF，不能只信 fulltext。

### 问题 4：4 个 .docx 附件无全文

`qinjian-survey-r1/r2/r2b` 那几个 docx 的 fulltext 返回 404。Zotero 的全文提取主要面向 PDF。

**记录，未修**。需要时用 python-docx 直接解析。

### 问题 5：疑似重复条目

`F8MJMUDX` 与 `J5DP3WXY` 标题完全相同（`qinjian-survey-r2-reconcile.docx`）。本地 API 没有去重接口，Zotero 桌面端有。需要人工确认后合并。
