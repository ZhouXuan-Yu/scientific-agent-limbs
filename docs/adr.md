# 设计决策记录（ADR）

每条约束背后都有一个具体事故或一个明确取舍。这里逐条展开，包括那些当时判断错了、后来更正的部分。

`README.md` 的「设计约束」是结论，本文件是过程。

## ADR-001 探活必须多轮，且不能把 `started=true` 直接当作误判

**日期** 2026-10-19　**状态** 已采纳，附更正

**背景**

同一天两次 `health.mjs` 报 `DSH started=true`（07:45 耗时 60.8 秒，07:53 耗时 14.3 秒）。当时我凭「探活失败 + 随后出现新启动行」判定为探活误判导致的误重启，并写进了文档。

后来用户确认：那两次都是他自己关掉了 DSH 窗口。

**更正**

那两次拉起完全正确。`started=true` 是事实，不是误报。

真正的问题在我的推理：**「探活失败 + 出现新启动行」在「用户关窗」和「探活真失败」两种情况下表现完全一致**。缺少关闭事件这一侧的证据时，把结果归因为系统缺陷是没有依据的。

**决策**

保留多轮探活（三轮、间隔 400 毫秒、任一通即算活着），但理由改为「降低未来真误判的概率」，不再声称它修复了已经发生的 bug。

**代价** 每次检查多花最多 0.8 秒。

**教训** 现象相同不等于原因相同。诊断结论必须写清依赖哪一侧的证据，以及缺失的那一侧可能是什么。

## ADR-002 进程还在但端口不通时，绝不 spawn

**日期** 2026-10-19　**状态** 已采纳

**背景**

这条不是对 ADR-001 的修补，而是补一个**尚未发生**的缺口。

DSH 和 Zotero 都是单实例应用。如果进程活着但端口卡住（比如主线程阻塞、正在重启），spawn 新实例会让旧实例退出，正在跑的任务随之中断。Zotero 则可能抢数据库锁、弹重复窗口。

**决策**

判定顺序改为：端口多轮探活 → 不通则查进程数 → 进程数为 0 才 spawn；进程数大于 0 则再等 15 秒端口，仍不通就返回 `refusing to spawn` 并报错。

**代价** 进程真卡死时不会自动恢复，需要人工介入。这个代价是主动选的：宁可上报「不通」，也不擅自杀掉用户正在用的东西。

## ADR-003 拉起是可见动作，必须留痕

**日期** 2026-10-19　**状态** 已采纳

**背景**

两个都是 GUI 应用。被拉起时会弹主窗口，可能抢焦点，Zotero 还会触发一次同步。这些都发生在用户不知情的情况下。

**决策**

`health.mjs` 的输出保留 `notes` 行，任何自动拉起都写明方式（`spawn` / `powershell`）。审计日志里同样记一条 `launch`。

**代价** 输出多一行。

## ADR-004 桌面应用的写入能力必须由人授权

**日期** 2026-10-19　**状态** 已采纳

**背景**

Zotero 10+ 的本地 API 支持写，但每个写请求需要本地 API key。这个 key 无法预先配置，只能通过 `POST /api/local/authorize` 在运行时申请，弹窗由用户在 Zotero 里点确认。

**决策**

接受「第一次必须有人在」。用户选 Always Allow 后 key 长期有效，按 Server-ID 分区缓存，撤销权始终在用户手里（设置 → 高级 → Clear Write Authorizations）。

**代价** 全新环境无法全自动运行。这一点在 ARCHITECTURE.md 的局限表里写明，不掩饰。

## ADR-005 依赖桌面会话已登录

**日期** 2026-10-19　**状态** 已采纳（环境限制，非选择）

**背景**

两个应用都是 Windows GUI 程序。锁屏、远程断连、无人值守场景下，「能拉起」这个结论不成立。

**决策**

明说，不假装支持。所有相关文档里都写了这条限制。

**代价** 无法部署为无人值守服务。如果要真正服务化，需要换非 GUI 的接入方式，那是另一个工程。

## ADR-006 并发调用必须单飞

**日期** 2026-10-19　**状态** 已采纳

**背景**

并发测试首轮，三个 `send` 同时进入 `ensureRunning`，各自判定未运行，各自 spawn，输出三行「已自动拉起」。DSH 的单实例锁托住了结果，但同一个实例被反复顶掉没有意义，真实任务并行时会变成不可预测的启动延迟。

**决策**

在 `dsh-core.mjs` 的 `ensureRunning` 外层加进程内单飞：并发调用共用同一个 in-flight Promise，完成后释放。

**代价** 单飞只在单进程内有效。多进程并发调用仍需文件锁，当前没有这个场景，不做。

**关于耗时** 修复后同一测试从 29883 毫秒降到 6124 毫秒，但这个对比有水分：首轮那 29.8 秒里大部分是 DSH 冷启动，不是并发开销。锁的作用是消除重复 spawn，不是提速。这个归因不能混。

## ADR-007 审计不能影响主流程

**日期** 2026-10-19　**状态** 已采纳

**背景**

审计日志要记录所有动作的成败与耗时。但写日志本身可能失败：目录不可写、磁盘满、文件被占用。

**决策**

所有审计写入都用 try/catch 包围，失败静默。审计模块缺失也不影响调用方。

**代价** 审计可能有缺口，而且这种缺口是无声的。这个取舍在「诊断价值」和「可用性」之间选了后者。

**已知不足** 失败路径的正确性只有代码逻辑保证。`recentFailures` 长期为空不是因为记录功能可靠，而是因为确实没失败过。这条证据强度比真实数据跑出来的结论弱一档。

## ADR-008 同名不同物：两条 send 路径都要接

**日期** 2026-10-19　**状态** 已采纳

**背景**

首次接入审计时只改了 `dsh-core.mjs` 的 `send`。结果 `audit.mjs query --actor dsh` 返回空，但下发本身是成功的。

原因：`dsh.mjs` 的命令行有自己一套 `submit` / `waitFor`，根本不走 `dsh-core`。两条实现并存，我按模块名想当然地以为只有一条。

**决策**

两条路径都接。文档里把这条写死，提醒后续改动时不要只看模块名。

**教训** 「同名」在代码里是最危险的相似性。改动前先确认调用链，而不是确认文件名。

## ADR-009 无效的 collection key 不会报错，而是静默返回全库

**日期** 2026-10-19　**状态** 已采纳

**背景**

小研在执行一次分类统计时实测发现：向不存在的 collection key 请求 `/collections/<key>/items/top`，Zotero 本地 API **不返回 404，而是返回全库条目**。

实测数据：错误 key `77736B99W` 的 `/items/top` 返回 55、`/items` 返回 75，而全库基线正是 55 与 76。只有 `/collections/<key>` 本身才真正返回 404。

**为什么要紧**

这个错误不报错、不回空、数字还在合理范围。拿错误 key 去做分类统计，会得到一个看起来正常的结果，然后被当成某个分类的真实规模。单纯看返回值无法发现。

**决策**

`zotero-core.mjs` 新增 `collectionStats(key)`：先 GET `/collections/<key>` 确认存在（404 则直接报错），再取 `/items/top` 的 `Total-Results` 与 `meta.numItems`。任何按分类统计的代码都走这个入口，不直接读 Total-Results。

同时把两种口径写进返回值：`topItems` 是真正的文献条目数（不含附件与笔记），`allObjects` 是含子条目的对象总数。两者都成立，但必须说清楚报的是哪一个。

**教训** 无错的沉默比报错更危险。凡是一个接口在输入错误时仍返回合理数据，就必须在客户端先验证输入。

## ADR-010 投递必须有对象盯着，团队任务要等到对话真正安静

**日期** 2026-10-19　**状态** 已采纳

**背景**

向群聊投一条任务后，Chief 先判断分工（seq 5）、修正错误输入（seq 6）、派给小研（seq 7），小研执行（seq 8–9），Chief 复核（seq 10）。整个过程五分钟，而我投完就去看别的了，最后是用户告诉我「处理完了」。

两个问题：

1. 手动投进群聊的消息没有等待者，也没有产物回收，是孤儿。
2. `dispatch --via room` 只等 Chief 的第一个 `turn/end`，而团队任务通常有多轮：接单、派单、成员执行、复核。等第一轮就返回，会错过后面所有。

**决策**

一、所有投递走 `dispatch`，不手投。手投的没有任务单、没有状态、没有回收。

二、`--via room` 的完成判据改为「群聊日志安静」：投递后轮询 `rooms[].log` 的 seq，连续 90 秒无新增才认为团队完成，并返回这期间的全部新条目。单轮 `turn/end` 不足以代表团队任务结束。

**代价** 每个团队任务至少多等 90 秒。这个代价必须付：早返回的代价是漏掉一半过程，而且漏了也没人知道。

**教训** 「等到第一个信号」与「等到结束」是两回事。多轮协作里，前者只说明事情开始了。
