# scientific-agent-limbs

给 AI 智能体装上手和脚。

不是又一个 Agent 框架。是 12 个可以用命令行单独运行的小模块，用来解决三件具体的事：**让外部程序真的动起来、知道它们什么时候做完了、留下能被人复核的记录。**

零第三方依赖，只用 Node 标准库。

---

## 你可能遇到过这些

你让 AI 读完十篇论文做一张对比表。它给了你一份很漂亮的东西，每篇一行。你问其中一个数字哪来的，它说"论文里写的"。你没法验，只能信或不信。

你说"这条引用有问题，帮我核一下"。它回"已核实，DOI 正确"。实际上它看的是摘要页，DOI 是它从你的记录里抄的。

你把任务发给另一个 AI，然后去看别的了。两小时后回来，不知道它是做完了、做砸了，还是根本没开始。

这三个问题不是模型能力问题。它们分别是：**取证该由谁做、完成信号是什么、证据能不能倒查**。

## 它能做到什么（都是实测，不是设想）

**十篇学位论文，62 万字，二十几分钟一张对比表。**
从 2007 到 2025 十篇中文硕士学位论文，每篇提取八个维度，输出 10 行 12 列。每个性能数字标注原文行号，原文没写精度的写「未报告」——五篇确实没有，不是漏抄。

团队还自己给出了技术分期，并且列出五条争议，包括"先图像处理、后语料库的单线叙事不成立"这种推翻自己结论的判断。

**五条引用核验，抓出两条真错误。**
两条记录都写着"无 DOI"，实际都有。一条是中文期刊（`10.11992/tis.202309008`），一条是 CVPR（`10.1109/CVPR.2019.00264`）。

它还把页码问题分成了两类：CVPR 那篇的 2537-2546 和 2532-541 不是记录错误，是 CVF 版和 IEEE 版的页码口径不同。这个区别决定了是"改记录"还是"标注版本"。

**任务卡住会自己发现。**
任务单有 deadline，到期未完成由守护进程置为失败并写明原因。不会出现"发了任务，三天后才发现根本没跑"。

**8 秒知道对面干完了。**
不轮询 DSH 内部状态，不猜。事件落盘 + 阻塞命令，实测 8.06 秒唤醒。

## 核心能力

| 能力 | 实现 | 实测数据 |
|---|---|---|
| 拉起并探活桌面程序 | 端口多轮探活 → 查进程数 → 才 spawn | Zotero 冷启动 5.4 秒 |
| 进程守卫 | 进程活着但端口不通时拒绝 spawn | 不擅自杀掉你在用的实例 |

| 完成信号 | 事件落盘 + 阻塞等待 | 8.06 秒唤醒 |
| 一条命令下发 | 渲染 → 投递 → 等事件 → 回写 | 端到端 90.9 秒 |
| 并发不串 | 三路并行独立会话 | 12 项判据全过，6124 毫秒 |
| 团队协作下发 | 投群聊，负责人派单 | 派单→执行→验收→退修→通过 |
| 文献四层回链 | R 号 ↔ Zotero key ↔ 精读卡 ↔ 草稿标记 | 绑定 27/37 |
| 统一审计 | 六类动作落盘 | 含耗时与失败原因 |

| 故障注入 | 六类异常路径 | 13 项断言全过 |

## 快速开始

前置：Node.js ≥ 20、Zotero 10+（本地 API 写能力只有 10+ 有）、DSH Desktop，以及一个能执行命令并把长任务后台化的宿主 Agent。

```bash
# 1. 复制目录，保持相对位置
#    limbs/  tasks/  dsh-plugin/

# 2. 配置
cp limbs/config.example.json limbs/config.json
#    改：workspace、zotero.exe、dsh.exe、两个日志路径

# 3. 自检
node limbs/config.mjs      # 每一项都要 ok
node limbs/health.mjs      # RESULT: OK

# 4. 验收
node limbs/test-tasks.mjs     # 任务单状态机，18 项
node limbs/test-failure.mjs   # 故障注入，13 项
```

不写配置也能跑——默认值按平台推导，只是路径大概不对。`config.mjs` 会逐项告诉你哪个不存在。

## 为什么这些结论可信

这是这个项目最在意的部分。

**每个能力都有实测记录。** 测过什么、没测什么写清楚。比如"Zotero 写入通过"这条，附件上传只探测到通道开启，真实文件上传标为未测。

**故障路径单独验。** `test-failure.mjs` 用过期版本号写 Zotero，拿到 412；再用正确版本号写成功（204）作为对照组——证明那个 412 确实来自版本过期，不是别的原因。

**判断错了会写进 ADR。** 有一次我把两次正常的窗口关闭后拉起误判为"探活误判"，后来发现是自己的推理漏洞，这条更正留在 [docs/adr.md](docs/adr.md) 的 ADR-001 里。十一条 ADR，记录的都是具体事故和当时的错误判断。

**学理上有依据的地方会注明。** 判断"任务做完了没"这个问题的学术名称是 Distributed Termination Detection（Dijkstra & Scholten, 1980），终止条件是「所有进程 passive 且所有通道为空」。只看群聊不看成员 session，就会漏掉一半工作——这个错犯过一次，写进了 ADR-011。

## 局限

列出来反而更可信：

- 三个应用都是单实例，被外部重启时正在跑的任务会断
- Zotero 写授权只能由人在弹窗点，全新环境第一次必须有人在
- 「自动唤醒」靠后台任务 + 宿主等待机制，不是平台级执行注入
- 群聊里并行任务的消息会混在一起，现在靠串行门禁避免
- 全部依赖桌面会话已登录，锁屏或无人值守场景不成立
- 文献匹配靠标题字面，中文简称和"作者+年份"式提及会漏
